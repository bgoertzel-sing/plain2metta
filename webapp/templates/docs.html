Plain2MeTTa

Plain2MeTTa is a source-preserving specification compiler. You write specs in Plain format — structured English with lightweight markers — and the compiler produces MeTTa atoms, a JSON intermediate representation, and a diagnostics report with validation obligations, coverage analysis, and open questions.

What this is A spec analysis and validation scaffold. It extracts concepts, requirements, acceptance tests, security/privacy obligations, information-flow patterns, and ML methodology checks from structured English specs. It does not generate executable code.

Quick Start

Install & Run (CLI)

git clone https://github.com/bgoertzel-sing/plain2metta
cd plain2metta

# Compile a spec → .json + .metta + .diag files
PYTHONPATH=src python3 -m specatom_hs.cli examples/auth_service.plain

# One output format to stdout
PYTHONPATH=src python3 -m specatom_hs.cli --metta examples/minimal.plain
PYTHONPATH=src python3 -m specatom_hs.cli --diagnostics examples/task_manager.plain
PYTHONPATH=src python3 -m specatom_hs.cli --json examples/auth_service.plain

# Run all tests
PYTHONPATH=src python3 -m unittest discover -s tests -v

Python API (3 lines)

from specatom_hs.passes import compile_source
from specatom_hs.backends.petta import emit_reified_atoms

doc = compile_source("***definitions***\n- :Task: is work.\n", "minimal.plain")
atoms, refusals = emit_reified_atoms(doc)

Web App

The web app lets you paste a spec and see all outputs instantly in your browser.

# Install Flask (one-time)
pip install flask

cd webapp
python app.py

# Open http://localhost:8080

The web UI has three output tabs — Diagnostics, MeTTa Atoms, and JSON — plus a summary bar showing object/check counts at a glance. Use the example dropdown to load bundled specs.

Plain Format

Plain specs are structured English documents using ***section*** headers and - bullet items. Concepts are marked with colons (:Concept:), requirements get explicit IDs ([id:REQ-1]), and tests declare coverage ([covers:REQ-1]).

Sections

Sections are delimited by ***name*** markers. Recognized section types:

SectionPurpose
***definitions***Define domain concepts, entities, and glossary terms
***functional specifications***Describe what the system should do (requirements)
***acceptance tests***Given/When/Then test cases linked to requirements
***implementation requirements***Technical constraints and platform requirements

Concepts & Markers

The compiler recognizes several concept markers:

SyntaxMeaningExample
:Name:Concept definition (first use) or reference:User: can log in
[def:Name]Explicit concept definition[def:Session] is a record…
[ref:Name]Explicit concept referencevalidates [ref:AuthToken]
[concept:Name]Concept (definition in definitions section, reference elsewhere)[concept:Task]
[external:name]External dependency (not defined in this spec)[external:argon2id]
Unresolved concepts If you reference a concept that's never defined or marked external, the compiler creates an unresolved concept question — a blocking validation obligation that asks you to define it or mark it external.

Requirements & Test Coverage

Requirements can be explicitly labelled for coverage tracking:

***functional specifications***
- [id:AUTH-1] The service shall authenticate a :User: with email and password.
- [id:AUTH-2] The service shall reject invalid login attempts.

***acceptance tests***
- [covers:AUTH-1] Given a known :User: with a correct password, when login is called, then an :AuthToken: is returned.
- [covers:AUTH-2] Given an invalid password, when login is called, then no :Session: is created.

The compiler checks:

  • Every requirement has at least one acceptance test (or an open question is raised)
  • Every acceptance test covers at least one requirement
  • Coverage labels resolve to exactly one requirement (duplicates and missing labels raise questions)
  • Orphan tests without coverage targets get flagged

Full Example

***definitions***
- :User: is a person allowed to authenticate with the product.
- :Session: is a server-side record proving that a :User: has recently authenticated.
- :AuthToken: is a signed bearer credential bound to one :Session:.
- :PasswordHasher: is provided by [external:argon2id].

***functional specifications***
- [id:AUTH-1] The service shall authenticate a :User: with email and password,
  then create a :Session: and issue an :AuthToken:.
- [id:AUTH-2] The service shall reject login attempts when :PasswordHasher:
  verification fails.

***acceptance tests***
- [covers:AUTH-1] Given a known :User: with a correct password, when the login
  endpoint is called, then the response contains an :AuthToken:.
- [covers:AUTH-2] Given an invalid password, when the login endpoint is called,
  then no :Session: is created.

MeTTa Atoms Output

The PeTTa backend emits reified atoms grouped by category: source files, spans, sections, items, objects (concepts, requirements, tests, questions), validation obligations, checks, and provenance links. Each atom preserves exact source spans for traceability. 

;; Example atoms (simplified)
(plain-file file-abc123 "auth.plain" sha256:...)
(source-span span-001 file-abc123 0 42 1 1)
(spec-object concept-User ConceptObject TemplateParsed)
(ConceptName concept-User "User")
(ConceptStatus "User" "defined")
(spec-object req-AUTH1 RequirementObject TemplateParsed)
(RequirementLabel req-AUTH1 "AUTH-1")
(Covers test-1 req-AUTH1)

JSON Output

The JSON output is a complete structured representation of the compiled document: files, sections, items, source spans, objects, validation obligations, checks, and derived facts. Useful for programmatic downstream processing.

Diagnostics Report

The diagnostics report is a Markdown document summarizing validation results:

  • Summary counts — total objects, obligations, pass/fail/unknown checks, refusals, questions
  • Per-property breakdown — each validation property with its pass/fail/unknown counts
  • FAIL checks — structural validation failures
  • UNKNOWN checks — items needing human review or additional evidence
  • Questions — blocking review questions the spec raises
  • Backend refusals — items the PeTTa backend cannot safely process

How Validation Works

The compiler runs an ordered series of passes that create validation obligations (things that need to be verified) and check records (the verification outcome). Checks are one of:

StatusMeaning
PassEvidence found — obligation satisfied
FailStructural violation detected
UnknownInsufficient evidence — human review needed

When a check is Unknown, the compiler typically creates a Question Object describing what needs to be resolved. Questions block specific validation obligations and serve as a structured review checklist.

Security & Privacy Validation

If your spec mentions secrets, tokens, passwords, PII, authentication, access control, webhooks, or destructive actions, the compiler creates conservative security/privacy obligations. These check for evidence of:

  • Secret storage and handling (no hardcoding, vault, env vars)
  • Log redaction for secrets
  • Credential rotation and expiry
  • PII consent, minimization, retention, encryption
  • Data classification and purpose limitation
  • Access boundaries (RBAC, least privilege)
  • Session management (MFA, timeouts, token refresh)
  • API abuse protection (rate limiting, brute-force)
  • Webhook request authenticity
  • Safe error disclosure
  • Destructive action safety (confirm, backup, rollback)

Information Flow Validation

When specs mention data flows, pipelines, inputs/outputs, or dependencies, the compiler extracts component-level DataFlowEdge and TemporalOrderEdge atoms and runs graph analysis including cycle detection, bottleneck detection, fan-in/fan-out analysis, connected components, and critical-path analysis.

ML & Time-Series Methodology

For specs involving ML, prediction, or time-series work, the compiler checks for: metric declaration, horizon/frequency, reproducibility evidence, train-only preprocessing, temporal split ordering, baseline comparison, and uncertainty reporting.

CLI Reference

PYTHONPATH=src python3 -m specatom_hs.cli [OPTIONS] FILE.plain

Options:
  --json          Write JSON to stdout
  --metta         Write MeTTa atoms to stdout
  --diagnostics   Write diagnostics report to stdout
  --all           Write .json, .metta, .diag files beside the input

If no format flag is given, --all is the default.

Python API Reference

from specatom_hs.passes import compile_source, compile_path
from specatom_hs.backends.petta import emit_reified_atoms, emit_reified_atoms_grouped
from specatom_hs.backends.petta import refuse_executable_skeleton
from specatom_hs.backends.diagnostics import format_diagnostics_report, diagnostics_summary

# Compile from string
doc = compile_source(text, "filename.plain")

# Compile from file
doc = compile_path("path/to/spec.plain")

# Get MeTTa atoms
atoms, refusals = emit_reified_atoms(doc)
atoms_grouped, refusals = emit_reified_atoms_grouped(doc)  # with section headers

# Get diagnostics
report = format_diagnostics_report(doc)     # Markdown string
summary = diagnostics_summary(doc)          # dict with counts

# Check executable-skeleton refusals
skeleton_refusals = refuse_executable_skeleton(doc.objects)

Known Limitations

Not yet supported
  • Full Plain grammar — the parser handles the most common structural patterns but not the complete Plain language spec
  • Deep English semantics — analysis is keyword/pattern-level, not NLP-based
  • Executable skeleton generation — the compiler refuses to generate runnable code from raw text specs; all executable-generation requests produce explicit refusal records
  • Remote/published repository workflows — designed for local/offline use

These are intentional design boundaries. The compiler is conservative by default: it surfaces what it cannot verify as Unknown checks and Question Objects, rather than making unsupported claims about spec semantics.
